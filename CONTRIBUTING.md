# Contributing

Lens Image Explorer runs inside Lens Desktop. Read [AGENTS.md](AGENTS.md) before changing it.

## Track the work

- Search [GitHub Issues](https://github.com/devnetge/lens-image-explorer/issues) before opening an issue. Reuse an issue for ordinary follow-ups; separate distinct outcomes.
- Keep the issue's scope, acceptance criteria, validation, and status current in the [project](https://github.com/orgs/devnetge/projects/2).
- Use a short branch such as `feat/image-search`, `fix/image-size`, or `docs/usage`. Add its exact full name as a label to every associated issue, preserving other labels.
- Keep PRs focused. Describe the outcome and validation, link the issue, and use `Closes #123` when the PR resolves it. State any verification limits.

## Build and verify

The authoritative extension guide is generated by the current Lens build at:

```text
~/.k8slens/extensions/extension-development-instructions/README.md
```

Follow that guide for setup, supported APIs, host dependency versions, and reload logs. Do not infer extension capabilities from Lens internals or package names. If a capability is missing, follow its missing-capability workflow. Re-read the guide after upgrading Lens; host-provided dependencies must use compatible `^<version>` ranges.

From the extension directory registered with Lens:

```sh
npm install
npm run build
npm test
```

Run `npm run build` after every source or dependency change: Lens loads the single CommonJS bundle at `dist/index.js`. Check the renderer log for successful reload, then verify the affected Images or Pod-details flow in Lens. Record automated checks and live verification separately. Documentation-only changes need no build.

## Dependency updates

Dependabot checks npm dependencies weekly on Monday at 09:00 Europe/Lisbon. It groups minor and patch development-tool updates and proposes major tooling updates separately. React type definitions receive patch updates only, keeping them on the host's React 19.2 minor. Review update PRs and run the build and tests before merging.

The configuration excludes Lens-provided packages (`@k8slens/*`, `@lensapp/*`, React, MobX, and Zod) from version and security update PRs. Their existing `^<host-version>` ranges must continue to accept the current Lens build; a newer minimum can prevent loading even within the same major version. Host security fixes require a compatible Lens update. After upgrading Lens, re-check its generated extension guide, sync host dependency ranges, and revisit the React type rules. Dependabot continues to propose security fixes for eligible extension-owned dependencies.

## Commits and release notes

- Use one short conventional commit subject, aiming for 50 characters and never exceeding 60; for example, `fix: wrap runtime image IDs`. Keep PR titles similarly concise.
- Use your configured Git identity. Do not add co-author, generated-by, or other attribution trailers to commits or PR descriptions.
- Keep `README.md`, `package.json`, and `CHANGELOG.md` accurate. Use semantic versioning: patch for fixes, minor for compatible additions, major for breaking changes. Follow the host guide's rules for published and unpublished versions, and keep the changelog heading aligned with the version.
- Release publication is a maintainer action requiring explicit owner authorization. Use the supported Lens publishing workflow described in the host guide.

## Public examples and screenshots

Use synthetic cluster, namespace, workload, account, and repository names in examples. Keep credentials, tokens, kubeconfigs, private URLs, and identifying environment details out of public issues, PRs, logs, and images. Take screenshots of the actual extension in Lens with permission, and review them for sensitive information before sharing.
